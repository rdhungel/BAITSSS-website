Software Development & Verification

How BAITSSS Desktop V1 was engineered, verified, and prepared for release.

BAITSSS Desktop V1 is the first release version of the desktop software. This page records the software-engineering controls behind it: what changed during modernization, how the scientific calculation is protected, what is tested automatically, how runs remain reproducible, and which elements of mature scientific-software practice are already established or still developing.

Current stage

First-release validation and final software cleanup

The core desktop system is implemented. Current work is concentrated on final validation, authority cleanup, human workflow checks, release acceptance, documentation, and controlled packaging. Institutional-scale maturity is not claimed.

01 · Development scale

A research implementation was converted into controlled desktop scientific software.

The modernization was not limited to a graphical interface. It introduced an installable Windows product, project and run lifecycle management, controlled data preparation, a stable science execution path, recovery, results authority, provenance, automated equivalence checks, release tooling, and documentation while retaining a frozen scientific reference.

02 · Software assurance

Mature-software elements, stated individually.

The labels below distinguish an implemented control from a control that is still expanding or not yet mature. This is intended to let a software engineer assess the system without relying on promotional claims.

Version control and baselines

ESTABLISHED

Git history is used with a frozen V7 scientific reference and a separate V8 integration authority. Scientific reference state and current development state are explicitly distinguished.

Scientific configuration control

ESTABLISHED

Core V8 scientific execution files are protected by recorded source identities. A source-lock mismatch requires explicit integration review rather than silently updating the accepted baseline.

Scientific regression / equivalence

ESTABLISHED

Modernized execution is checked against the frozen scientific reference. The strongest completed case is a 3,096-hour Kansas whole-AOI V7↔V8 equivalence proof, supplemented by shorter and extended verification cases.

Unit, contract and integration testing

EXPANDING

Pytest-based checks cover engine contracts, model parameters, project lifecycle, Results authority, spatial transforms, viewer adapters, NLDAS transaction behavior, run readiness, resume determinism, storage compaction and related contracts. The suite is substantial for a first release but is not yet comparable in breadth to mature institutional codes with hundreds of cases.

Continuous integration

ESTABLISHED

GitHub Actions runs dedicated V8 proof workflows, including science source locks, runtime authority, numerical comparator contracts, project lifecycle, spatial math, deterministic resume and Data-to-Run readiness checks.

Deterministic restart and recovery

ESTABLISHED

Checkpoint and resume behavior is treated as a scientific property, not only a convenience. Restarted execution is tested so interruption does not alter the validated numerical trajectory.

Input validation and readiness gates

ESTABLISHED

AOI, static layers, NLDAS completeness, project period, data-source state and Run readiness are validated before scientific execution. Invalid or incomplete configurations are rejected rather than passed silently to the kernel.

Parameter authority

FINAL AUDIT

Configurable scientific parameters are being traced from saved Advanced Settings through run-local constants, runtime contracts and the final science kernel. Duplicate fallbacks and hard-coded literals are being classified so each configurable quantity has one canonical authority.

Immutable run inputs

ESTABLISHED

Run-local vegetation inputs and configuration are frozen for execution and provenance. Scientific execution therefore does not depend on a mutable user-interface state after a run has begun.

Architecture and authority separation

ADVANCED

Runtime authority, science bridge, project state, results authority, shared spatial viewer components, storage and UI concerns have been separated and progressively consolidated. Remaining duplicate authority is actively audited rather than accepted as permanent architecture.

Data and storage integrity

ESTABLISHED

Hourly storage compaction is verified for dimensions, georeferencing, datatype, nodata and pixel-value identity before replacement. Checkpoint identity and Results semantics are preserved across storage optimization.

Results authority

ESTABLISHED

Results are bound to the selected simulation/run rather than inferred from whichever files happen to be newest. Scientific export and pixel/time-series access are being consolidated around explicit run authority.

Failure handling and observability

EXPANDING

Run failures, recovery state, readiness failures and lifecycle defects are surfaced and tracked. Final human validation continues to exercise abnormal paths, long-run behavior and UI state transitions.

Performance engineering

ESTABLISHED

The scientific engine was reorganized around RAM-resident state, reduced materialization and spatial execution improvements. Performance changes are accepted only when numerical behavior remains equivalent to the reference.

Reproducibility and provenance

ESTABLISHED

Runs retain project period, run-local configuration, data/input identity, runtime authority and output association. Release work also verifies that production execution does not depend on developer-specific paths.

Dependency and runtime control

ESTABLISHED

BAITSSS Desktop ships with a private scientific runtime rather than relying on an uncontrolled system Python installation. Packaging preflight checks the runtime payload used by the released application.

Installer and release packaging

FINAL VALIDATION

Windows installer identity, packaged runtime, release manifests, documentation payload and release acceptance are part of the controlled build route for BAITSSS Desktop V1.

Documentation

EXPANDING

User guidance, capability documentation, release acceptance records and software-development evidence are maintained. Developer/API documentation is less mature than the user-facing and validation record.

Mandatory review governance

NOT YET MATURE

Review and isolated-branch workflows are used, but repository-level governance is not yet equivalent to mature institutional projects where protected branches, mandatory independent review and required CI checks are enforced for every integration.

Independent verification and validation

NOT YET ESTABLISHED

Most software verification has been performed within the BAITSSS development effort. Independent external software V&V and a long record of third-party operational use have not yet been accumulated.

Regression breadth and field exposure

EARLY

Validation depth on selected authoritative trajectories is strong, but the software has not yet accumulated the hundreds of configurations, edge cases, platforms, contributors and years of field exposure characteristic of long-lived scientific codes.

Security and dependency assurance

LIMITED

Runtime control and packaging reduce environmental uncertainty, but BAITSSS does not currently claim a formal software-security audit, institutional cybersecurity certification or long-term dependency-vulnerability program.

03 · Scientific protection

The primary release requirement is that software modernization does not silently change the science.

For a stateful evapotranspiration and soil-water model, code cleanup is acceptable only when the scientific trajectory is preserved or a scientific change is deliberately reviewed and documented.

01 · FROZEN REFERENCE

V7 remains the external scientific reference.

The validated V7 implementation is retained as a frozen comparison authority. V8 modernization is allowed to differ structurally, but release acceptance requires behavioral and output evidence.

02 · SOURCE LOCK

Critical V8 science authorities are identity-locked.

Selected execution files have recorded Git-blob-equivalent identities. A mismatch is treated as a review event, not as an automatic baseline update.

03 · LONG-RUN EQUIVALENCE

Seasonal state propagation has been compared directly.

The 3,096-hour Kansas whole-AOI V7↔V8 comparison provides stronger evidence than isolated spot checks because soil-water, ET and irrigation state propagate from hour to hour.

04 · RESTART DETERMINISM

Recovery is verified against uninterrupted execution.

Resume behavior is tested so checkpoint recovery does not introduce a second scientific path. Storage optimization is similarly required to preserve exact retained values and metadata.

05 · PARAMETER TRACEABILITY

Configurable parameters are traced to the kernel.

The current parameter-authority audit follows each engine-connected Advanced Setting from saved state to generated run constants, runtime contract and final value reaching science.

06 · RELEASE GATES

Science verification is part of software release acceptance.

Equivalence tools, runtime authority checks, packaging checks, no-developer-path tests and lifecycle contracts are integrated into release-oriented workflows rather than maintained as informal notes.

04 · Architecture

Authority is being reduced to explicit layers.

The modernization direction is one canonical authority for each responsibility, with small adapters between layers rather than duplicated science or duplicated UI state.

01

Desktop / UI

Project creation, AOI, data selection, Run, Results, settings and human-readable status.

02

Project & run state

Saved project authority, frozen run configuration, readiness, lifecycle and recovery identity.

03

Data preparation

Satellite, weather, static layers, conditioning and validation transformed into controlled run inputs.

04

Science execution

Runtime adapter and protected BAITSSS scientific kernel with controlled parameters and state propagation.

05

Results & provenance

Run-bound outputs, storage, scientific export, reports and traceability back to the executed configuration.

05 · Mature-code comparison

BAITSSS now uses several of the same assurance mechanisms as mature scientific codes. It has not yet earned their operational maturity.

BAITSSS Desktop V1

Strong verification depth for a first release

BAITSSS has a frozen scientific baseline, source locks, numerical equivalence checks, deterministic restart testing, CI, input/readiness contracts, provenance, packaged-runtime control and release acceptance infrastructure.

The current limitation is breadth: fewer independent test configurations, fewer external users, less contributor diversity, and little accumulated release history.

Long-lived institutional codes

Broader accumulated assurance

MODFLOW 6, for example, reports a full test suite of more than 750 cases and requires passing CI before a pull request can merge. WRF automatically performs regression testing on pull requests while explicitly distinguishing regression success from scientific validation of new changes.

Those projects also benefit from years or decades of external use, multiple maintainers, many model configurations and institutional governance. BAITSSS does not claim equivalence in those dimensions.

Interpretation: BAITSSS is no longer appropriately described as a research script. The evidence supports describing it as engineered scientific software in first-release validation, with several mature-code controls already implemented. The remaining gap to institutional maturity is primarily breadth, independent review, governance and accumulated operational history.
06 · Current stage

What is complete, and what still separates V1 from long-established scientific software.

Current classification

Engineered scientific software entering its first release.

The science execution path, desktop workflow, run lifecycle, recovery, Results, validation, provenance and packaging route are substantially implemented. Current development is concentrated on final authority cleanup, broad human validation, release acceptance and documentation rather than invention of a new scientific model.

Remaining maturity work

Evidence that can only be accumulated over time

  • broader regression and edge-case coverage
  • mandatory independent review and protected integration governance
  • independent external V&V and third-party beta use
  • published code-coverage and static-analysis metrics
  • formal security/dependency assurance
  • multiple maintained releases and backward-compatibility history
  • years of operational use across institutions and environments
07 · Reference framework

External software-assurance context used for this assessment.

NASA Software Assurance and Software Safety Standard. Defines systematic software assurance across the lifecycle, including verification, validation, reliability, safety, security and IV&V. NASA-STD-8739.8
MODFLOW 6 developer practice. Documents unit and integration testing, regression comparison, GitHub Actions CI, and a test suite exceeding 750 cases that must pass before merge. MODFLOW 6 Developer Guide
WRF automated regression testing. Runs test suites on pull requests and explicitly notes that regression success prevents unintended side effects in tested configurations but does not by itself validate new scientific behavior. WRF testing overview
